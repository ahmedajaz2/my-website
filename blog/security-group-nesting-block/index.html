🚫 Blocking Nested Security Groups in Entra ID

🗓️ Published: October 2026 | ✍️ Author: Ajaz Ahmed

Nested security groups are one of those things everyone uses and nobody audits. A group inside a group inside a group - and suddenly nobody can tell you who actually has access to the finance share. Microsoft just shipped something I have wanted for years: a disableNesting property that blocks other groups from being added as members of a security group. It is a small property with a big payoff. Here is what it does, how to turn it on, and where I would apply it first.

🧅 Why Nesting Is a Problem

Group nesting feels efficient. Instead of managing hundreds of individual memberships, you drop one role group inside another and reuse the structure. At enterprise scale, that convenience quietly becomes a liability. Access reviews lie: a reviewer sees "Finance-Readers" has 12 members and approves it, never realizing one of those members is another group with 400 people in it. Effective access turns invisible - answering "who can touch this confidential data?" means expanding every nested group recursively, and most teams never do. Workload support is inconsistent too: some provisioning flows, like SCIM, only honor direct memberships, so nested members silently lose access - or silently keep it where nobody notices. And deep nesting makes sign-in troubleshooting harder than it needs to be.

Take: if you cannot answer "who has access?" without running a script, your nesting has outgrown its usefulness.

🔧 What disableNesting Does

Microsoft added a disableNesting property to security groups. It defaults to false, so your existing groups behave exactly as they do today. Set it to true, and Entra ID refuses to add any group as a member of that security group - users, devices, and service principals can still be added directly, but group-in-group membership is blocked. Two things to know: it is per-group, not tenant-wide, so you choose which groups get the protection. And it is Graph API only for now - the Entra admin center does not expose the setting yet, so you will set it with PowerShell or a direct Graph call.

💻 Turning It On

Create a new security group with nesting disabled: 

$RequestBody = @{}
$RequestBody.Add("displayName", "Finance Auditors")
$RequestBody.Add("securityEnabled", $true)
$RequestBody.Add("disableNesting", $true)
$RequestBody.Add("mailEnabled", $false)
$RequestBody.Add("mailNickname", "Finance.Auditors")
$RequestBody.Add("description", "Security group for financial auditors - nesting disabled")

$Uri = "https://graph.microsoft.com/v1.0/groups"
$NewGroup = Invoke-MgGraphRequest -Uri $Uri -Method Post -Body $RequestBody
Write-Host ("Created group: {0}" -f $NewGroup.displayName)

For an existing group, set the same property with a PATCH request to /groups/{id}. You will need Group.ReadWrite.All permission for either call.

Take: make disableNesting=true part of your group creation template for anything sensitive, so new groups are born clean.

🎯 Where I Would Apply It First

You do not need to flatten every group on day one. Start where nesting hurts most: privileged access groups (admin roles, PAM, emergency access - nesting here is a standing invitation to privilege creep), groups guarding confidential data (finance, HR, legal - the ones auditors ask about), groups used in Conditional Access policies (a nested group in a CA policy is a policy whose scope you cannot see), and groups under access review (flatten before the next cycle so reviewers see real membership).

Take: pick your ten most sensitive security groups this week and set disableNesting on the ones with no legitimate nesting need.

📋 Audit What You Already Have

For existing groups, find the nesting before you block it. Compare memberOf against transitiveMemberOf for your sensitive groups - wherever the two differ, nesting is hiding members. Flatten the ones where nesting adds no real value, then set disableNesting so they stay flat.

💬 Closing Thoughts

Least privilege starts with knowing who has what. Nested groups were the blind spot - a convenience feature that made "who has access?" unanswerable at scale. disableNesting is a small, overdue control: simple, per-group, and exactly where it belongs. Use it on the groups that matter most, and your next access review will thank you.

  • ✅ Identify your ten most sensitive security groups and check them for nesting (memberOf vs transitiveMemberOf).
  • ✅ Set disableNesting=true on sensitive groups with no legitimate nesting need.
  • ✅ Add disableNesting=true to your group creation template for new sensitive groups.
  • ✅ Flatten nested groups before the next access review cycle.
  • ✅ Review Conditional Access policies targeting groups - make sure you know the full effective membership.
